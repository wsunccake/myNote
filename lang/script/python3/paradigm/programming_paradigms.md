# Programming Paradigms / 編程範式

Programming Paradigms（編程範式）是指電腦解決問題的「思考方式」。隨着硬體效能提升與軟體複雜度增加，開發者從「如何一步步操作機器」演進到了「如何更抽象地描述意圖」。

---

## Imperative Programming / 命令式編程

- **簡介**:
  命令式編程是一種描述計算機執行指令的編程範式，它明確地控制程序的狀態和執行流程。程式碼基本上是一系列的指令，告訴計算機“如何” (How) 完成任務。

- **演進歷史**:
  這是最古老、最直接的編程範式，其思想直接源於馮·諾伊曼等早期計算機架構。早期的程式語言，如彙編語言、FORTRAN、COBOL，都是純粹的命令式語言。

- **核心概念**:
  - **狀態 (State)**: 程序中存在一個可變的狀態，由一組變數的值來定義。
  - **指令 (Instructions/Commands)**: 程式由一系列改變程序狀態的指令構成。
  - **順序執行 (Sequential Execution)**: 指令通常按照它們在程式碼中出現的順序執行，但可以透過控制流語句（如迴圈 `for`, `while`、條件分支 `if-else`、`goto`）來改變。

- **準則規範**:
  核心是使用語句（statements）來改變程序狀態。開發者必須詳細描述達成目標的每一個步驟。

- **優點**:
  - 模型簡單，與底層硬體操作方式貼近，易於理解和實現。
  - 對於小型、直接的任務，程式碼非常直觀。
  - 由於直接映射到底層機器指令，通常能獲得很高的執行性能。

- **缺點**:
  - 在大型程式中，狀態變化的複雜性會急劇增加（狀態爆炸），導致程式難以管理和推理。
  - 程式碼充斥著副作用（Side Effects），即可變狀態的修改，這使得程式碼的可讀性和可維護性變差。
  - 由於狀態共享和副作用，很難安全地進行並行計算。

- **應用實例**:
  - 大部分的底層系統編程、嵌入式系統、性能敏感的計算。
  - 幾乎所有主流語言都支持命令式風格，尤其是在編寫小型腳本或函式內部時。
  - 一個典型的 `for` 迴圈來計算總和：
    ```c
    int total = 0;
    for (int i = 1; i <= 10; i++) {
        total += i; // 直接修改 total 變數的狀態
    }
    ```

## Procedural Programming / 程序導向編程

- **簡介**:
  程序導向編程是命令式編程的一種演進，它將程式碼組織成稱為“程序”（Procedures）、“子程序”（Subroutines）或“函數”（Functions）的模塊。

- **演進歷史**:
  隨著程式規模的增長，單純的命令式編程（使用 `goto` 等）變得難以管理，導致了所謂的“麵條式代碼”。為了更好地組織程式碼和促進程式碼重用，程序導向的概念在 1960 年代末和 1970 年代初被提倡，並在 Pascal 和 C 等語言中得到廣泛應用。

- **核心概念**:
  - **程序 (Procedures)**: 將一系列相關指令分組為一個可命名的單元，可以接受輸入參數並可能返回值。
  - **模組化 (Modularity)**: 將複雜問題分解為更小、更易於管理的程序。
  - **程式碼重用 (Code Reuse)**: 一旦定義，程序可以在程式的不同地方被重複調用。

- **準則規範**:
  強調將程式碼分解為程序，並通過程序調用來組織程式流程。數據和操作數據的程序通常是分離的。

- **優點**:
  - 比純命令式編程更具結構化，提高了程式碼的可讀性和可維護性。
  - 通過模塊化促進了程式碼重用。
  - 易於追蹤程式的執行流程（從一個程序調用到另一個）。
- **缺點**:
  - 數據和操作數據的邏輯是分離的。數據通常是全域的或在程序間自由傳遞，這使得數據的狀態難以被有效追蹤和保護，容易被意外修改。
  - 隨著程式複雜度增加，大量的程序和它們之間的依賴關係會變得混亂，難以管理。

- **應用實例**:
  - C 語言是程序導向的典型代表。
  - 用於編寫作業系統、編譯器、數據庫等系統軟體。

    ```c
    // 數據結構
    struct Circle {
        float radius;
    };

    // 操作數據的程序
    float calculate_area(struct Circle c) {
        return 3.14159 * c.radius * c.radius;
    }

    int main() {
        struct Circle my_circle = { 5.0 };
        float area = calculate_area(my_circle); // 數據和操作分離
        return 0;
    }
    ```

## Declarative Programming / 宣告式編程

- **簡介**:
  宣告式編程是一種與命令式編程相對的編程範式。它專注於描述目標“是什麼”（What），而不是詳細闡述“如何”（How）達成。開發者只需表達計算的邏輯，而具體的執行步驟則由底層系統（如編譯器、解釋器或數據庫引擎）來決定。

- **演進歷史**:
  宣告式編程的思想很早就存在，但在數據庫查詢語言和邏輯編程中得到了最早和最廣泛的應用。隨著各種框架和領域特定語言（DSL）的興起，它在現代軟體開發中變得越來越重要和普遍。

- **核心概念**:
  - **表達邏輯而非控制流**: 程式碼專注於描述所需結果的屬性和它們之間的關係。
  - **無副作用 (或減少副作用)**: 通常不直接修改已存在的狀態，而是描述從輸入到輸出的轉換關係。
  - **高度抽象**: 將底層的執行細節（如迴圈、條件判斷、狀態管理）抽象化。

- **準則規範**:
  程式碼應該像是在描述一個事實、一個規則或一個最終目標，而不是一系列操作指令。

- **優點**:
  - 程式碼更簡潔、可讀性更高，因為它更接近問題本身的描述。
  - 由於執行細節被抽象化，底層系統可以進行更有效的優化（例如 SQL 查詢優化）。
  - 減少了因手動管理狀態和流程而產生的 bug。
  - 程式碼的意圖更加清晰。

- **缺點**:
  - 對於某些問題，描述“是什麼”比描述“如何做”要更困難。
  - 由於高度抽象，當出現問題時，除錯可能比較困難，因為無法輕易窺探底層的執行過程。
  - 不是所有問題都適合用宣告式的方式來解決，有時直接的指令控制更高效。

- **應用實例**:
  - **SQL**: `SELECT name FROM users WHERE country = 'Taiwan';` (你宣告需要什麼資料，而不是告訴數據庫如何一步步去查找和過濾)。
  - **HTML**: `<article><h1>標題</h1><p>段落內容。</p></article>` (你宣告頁面的結構，而不是編寫繪製像素點的程式)。
  - **React (UI 框架)**: `const UserProfile = ({ user }) => <div>{user.name}</div>;` (你宣告 UI 應該長什麼樣子，React 負責更新 DOM)。
  - **配置文件 (JSON, YAML)**: 宣告系統的配置，而不是編寫設置配置的腳本。

## Functional Programming, FP / 函數式編程

- **簡介**:
  函數式編程是宣告式編程的一種重要分支。它將計算過程視為數學函數的求值，並強調使用“純函數”（Pure Functions）和“不可變數據”（Immutability）。

- **演進歷史**:
  其理論基礎源於 1930 年代的 Lambda 演算。第一門主要的函數式語言 Lisp 在 1950 年代末出現。在很長一段時間裡，它主要活躍於學術界。近年來，隨著對並行計算、數據處理和系統可靠性需求的增加，函數式編程的思想被重新重視並被主流語言大量吸收。

- **核心概念**:
  - **純函數 (Pure Functions)**: 對於相同的輸入，總是產生相同的輸出，並且沒有可觀察的副作用（不修改外部狀態、不進行 I/O 操作等）。
  - **不可變性 (Immutability)**: 數據一旦創建就不能被修改。任何修改操作都會返回一個新的數據對象，而不是在原地修改。
  - **一等公民函數 (First-class Functions)**: 函數可以被當作普通變數一樣對待，可以賦值給變數、作為參數傳遞給其他函數、或作為其他函數的返回值。
  - **高階函數 (Higher-order Functions)**: 可以接受函數作為參數或返回一個函數的函數。`map`, `filter`, `reduce` 是典型的高階函數。
  - **函數組合 (Function Composition)**: 將多個簡單函數組合成一個更複雜的函數。

- **準則規範**:
  盡量使用純函數和不可變數據。通過函數組合來構建程式，避免顯式的狀態和迴圈。將有副作用的操作（如 I/O）與純邏輯分離。

- **優點**:
  - **易於推理和測試**: 純函數的行為是可預測的，極大地簡化了單元測試和除錯。
  - **適合並行/並發**: 由於數據不可變，從根本上避免了多線程環境下的競爭條件（Race Condition），無需使用鎖。
  - **模組化和可組合性**: 程式碼由許多小而獨立的純函數組成，易於組合和重用。

- **缺點**:
  - **學習曲線**: 對於習慣了命令式編程的開發者來說，需要轉變思維方式，學習曲線較陡。
  - **性能考量**: 過度創建新對象（由於不可變性）可能在某些場景下帶來性能和記憶體開銷（儘管現代 FP 語言有優化）。
  - **處理副作用**: 處理 inherently stateful 的操作（如 I/O、數據庫交互）相對複雜，需要藉助 Monads 等抽象概念。

- **應用實例**:
  - **純函數式語言**: Haskell, Lisp, F#, Clojure, OCaml。
  - **混合範式語言**: 幾乎所有現代語言（JavaScript, Python, Java, C#, Scala, Kotlin）都引入了函數式特性。
  - **大數據處理**: Spark, Flink 等框架大量使用 `map`, `reduce` 等函數式操作。
  - **前端開發**: React/Redux 架構深受函數式思想影響，特別是 Reducer 必須是純函數。
  - **Map, Filter, Reduce 操作**:
    ```javascript
    const numbers = [1, 2, 3, 4, 5];
    // 命令式寫法
    let sumOfSquares_imperative = 0;
    for (let i = 0; i < numbers.length; i++) {
      sumOfSquares_imperative += numbers[i] * numbers[i];
    }
    // 函數式寫法
    const sumOfSquares_functional = numbers
      .map((x) => x * x) // 轉換
      .reduce((acc, val) => acc + val, 0); // 聚合
    ```

## Logic Programming / 邏輯式編程

- **簡介**:
  邏輯式編程是宣告式編程的另一種形式，它基於形式邏輯。程式本身就是一組關於某个問題領域的“事實”（Facts）和“規則”（Rules），執行程式的過程就是對一個“查詢”（Query）進行邏輯推導和求解的過程。

- **演進歷史**:
  源於 1960 年代末和 1970 年代初的人工智慧研究，旨在創建一種可以表達邏輯和進行自動推理的程式語言。Prolog 是最著名和最具代表性的邏輯編程語言。

- **核心概念**:
  - **事實 (Facts)**: 關於對象及其關係的基本斷言，是無條件為真的語句。例如 `parent(john, mary).` 表示 "john 是 mary 的父親"。
  - **規則 (Rules)**: 定義了如何從已知事實推導出新事實的條件語句。例如 `grandparent(X, Z) :- parent(X, Y), parent(Y, Z).` 表示 "如果 X 是 Y 的父親且 Y 是 Z 的父親，那麼 X 就是 Z 的祖父"。
  - **查詢 (Queries)**: 向程式的知識庫提出問題，系統會嘗試找到滿足條件的答案。
  - **核心機制**:
    - **合一 (Unification)**: 嘗試使兩個邏輯項（term）在結構上匹配的過程，可以包含變數的實例化。
    - **回溯 (Backtracking)**: 當一條推導路徑失敗時，系統會自動返回上一個選擇點，並嘗試其他可能性。

- **準則規範**:
  程式由邏輯語句構成，開發者專注於定義問題域中的知識和關係，而不是設計算法步驟。

- **優點**:
  - 非常適合處理符號邏輯、專家系統、自然語言處理、數據庫查詢、約束滿足等問題。
  - 程式碼可以非常直觀地表示問題的邏輯結構。
  - 能夠優雅地解決一些用命令式編程難以表達的問題。

- **缺點**:
  - **應用領域相對狹窄**: 不適合進行大規模數值計算或圖形界面等任務。
  - **執行效率和可預測性**: 執行效率通常不高，且基於回溯的搜索機制可能導致性能難以預測。
  - **控制能力弱**: 開發者對程式的執行流程控制能力很弱。

- **應用實例**:
  - **Prolog, Datalog** 是主要的邏輯編程語言。
  - 應用領域：
    - **專家系統**: 模擬人類專家的決策過程。
    - **自動定理證明**: 在數學和計算機科學中證明定理。
    - **自然語言處理**: 分析語法結構。
  - **Prolog 家族關係範例**:

    ```prolog
    % Facts: 'parent(父親, 孩子).'
    parent(john, mary).
    parent(john, tom).
    parent(susan, john).

    % Rule: 'grandparent(祖父母, 孫子女).'
    % 如果 X 是 Y 的父母，且 Y 是 Z 的父母，那麼 X 就是 Z 的祖父母。
    grandparent(X, Z) :- parent(X, Y), parent(Y, Z).

    % Query: 誰是 mary 的祖父母?
    % ?- grandparent(GP, mary).
    % GP = susan
    ```

## Event-Driven Programming / 事件導向編程

- **簡介**:
  事件導向編程是一種程式執行流程由“事件”決定的編程範式。程式的核心是一個持續運行的“事件迴圈”（Event Loop），它等待事件的發生，然後將事件分派給相應的“事件處理器”（Event Handler）來處理。

- **演進歷史**:
  最早廣泛應用於圖形使用者介面（GUI）的開發，因為 GUI 的互動本質上就是由用戶的滑鼠點擊、鍵盤輸入等異步事件驅動的。隨著 Node.js 的成功，這種範式也被大規模應用於伺服器端開發，特別是處理高並發的 I/O 密集型任務。

- **核心概念**:
  - **事件 (Event)**: 由用戶、系統或其他程式產生的動作或狀態變化。例如：滑鼠點擊 (`click`)、網路請求到達 (`request`)、計時器到期 (`timeout`)。
  - **事件處理器 (Event Handler / Listener)**: 一個回調函數或方法，用於註冊並響應特定事件。當事件發生時，事件迴圈會調用它。
  - **事件迴圈 (Event Loop)**: 一個持續運行的迴圈，負責從事件隊列中獲取事件，並調用與之關聯的處理器。
  - **事件發射器 (Event Emitter / Dispatcher)**: 負責產生或觸發事件的對象。

- **準則規範**:
  程式結構圍繞著“當某事件發生時，執行某個操作”來組織。程式的流程是非線性的，由外部或內部的異步事件來驅動，而不是按照程式碼的順序線性執行。

- **優點**:
  - **高響應性**: 非常適合 GUI 和互動式應用，主線程不會被耗時操作阻塞。
  - **高並發 (I/O密集型)**: 通過非阻塞 I/O，可以在等待一個操作（如讀取文件、網路響應）完成時，去處理其他任務，極大地提高了資源利用率。
  - **鬆耦合**: 事件的產生者（發射器）和消費者（處理器）可以互不知曉，易於擴展和維護。

- **缺點**:
  - **回調地獄 (Callback Hell)**: 對於複雜的、有順序依賴的異步操作，多層嵌套的回調會導致程式碼難以閱讀和維護。
  - **狀態管理複雜**: 由於執行流程被打散在各個回調函數中，跨多個事件的狀態管理變得困難。
  - **除錯困難**: 追蹤非線性的事件觸發流程比追蹤線性程式碼要困難得多。

- **應用實例**:
  - **前端 JavaScript**: 幾乎所有的瀏覽器端 JavaScript 編程都是事件驅動的，用於響應 DOM 事件。
    ```javascript
    document.getElementById("myButton").addEventListener("click", function () {
      console.log("按鈕被點擊了！");
    });
    ```
  - **伺服器端 Node.js**: 其核心架構就是基於非阻塞 I/O 和事件迴圈，適合構建高性能的網路應用。
  - **GUI 框架**: Java Swing, .NET Windows Forms, Qt (C++) 等都使用事件驅動模型。

## Reactive / Dataflow Programming / 反應式/資料流編程

- **簡介**:
  - **資料流編程 (Dataflow)** 是一種將計算建模為數據在不同處理節點之間“流動”的範式。
  - **反應式編程 (Reactive Programming)** 是資料流編程的一種特定形式，它專注於處理“異步數據流”（Asynchronous Data Streams）以及“變化在系統中的傳播”。可以簡單理解為“觀察者模式 + 資料流 + 異步”。

- **演進歷史**:
  資料流的思想很早就存在於硬體設計和一些專業軟體中。試算表軟體（如 Excel）是最早、最直觀的反應式系統。現代反應式編程範式由 .NET 平台的 Rx (Reactive Extensions) 函式庫在 2000 年代末發揚光大，旨在解決複雜的異步 UI 事件處理，隨後被推廣到各種語言平台。

- **核心概念**:
  - **數據流 (Data Streams)**: 一切皆可為流。變數、用戶輸入、網路響應、計時器事件等，都可以被看作一個隨著時間推移而發出數據的序列。這個流可以發出零個或多個值，最後可能以一個完成或錯誤信號結束。
  - **可觀察對象 (Observable)**: 代表一個數據流。
  - **觀察者 (Observer)**: 訂閱 `Observable`，並對其發出的數據（`next`）、錯誤（`error`）和完成信號（`complete`）做出響應。
  - **操作符 (Operators)**: 純函數，用於對數據流進行轉換、組合、過濾等操作（如 `map`, `filter`, `merge`, `flatMap`）。操作符是反應式編程強大表達能力的關鍵。
  - **變化傳播 (Propagation of Change)**: 這是反應式系統的核心。當數據源發生變化時，所有依賴於該數據源的計算都會“自動”重新計算並更新。

- **準則規範**:
  程式的重點是創建和組合數據流。開發者以宣告式的方式定義數據流之間的依賴和轉換關係，而不是編寫命令式的控制邏輯。

- **優點**:
  - **優雅處理異步**: 提供了一套統一、強大的工具來處理各種異步操作（回調、Promises、事件等），有效避免“回調地獄”。
  - **程式碼意圖清晰**: 將複雜的異步邏輯以宣告式的方式表達出來，使程式碼更易讀、更接近業務邏輯。
  - **強大的組合能力**: 操作符提供了豐富的組合能力，可以輕鬆實現緩存、節流、防抖、重試等複雜功能。

- **缺點**:
  - **學習曲線陡峭**: 需要理解一套全新的概念（流、訂閱、操作符等）和思維方式。
  - **除錯困難**: 追蹤數據在複雜流中的變化路徑可能很困難（"Stack traces from hell"）。
  - **資源管理**: 需要注意訂閱的生命週期管理，否則容易造成記憶體洩漏。

- **應用實例**:
  - **試算表軟體 (Spreadsheets)**: 當你改變單元格 A1 的值，依賴 A1 的公式（如 `B1=A1*2`）會自動更新，這就是最經典的反應式系統。
  - **UI 開發**:
    - **RxJS (JavaScript)**: 廣泛用於 Angular 等前端框架，處理用戶輸入、HTTP 請求等異步事件流。
    - **Vue.js / Svelte**: 其核心的數據綁定和組件更新機制就是反應式的。
  - **後端服務**: Spring WebFlux (Java), Project Reactor 等用於構建反應式、高吞吐量的後端微服務。
  - **RxJS 範例 (搜尋框即時搜索)**:

    ```javascript
    import { fromEvent } from "rxjs";
    import {
      map,
      debounceTime,
      distinctUntilChanged,
      switchMap,
    } from "rxjs/operators";

    const searchBox = document.getElementById("search-box");

    fromEvent(searchBox, "input")
      .pipe(
        map((event) => event.target.value), // 獲取輸入值
        debounceTime(400), // 400ms 防抖
        distinctUntilChanged(), // 只有當值變化時才繼續
        switchMap((query) => ajax.get(`/api/search?q=${query}`)), // 發起網路請求
      )
      .subscribe((results) => {
        // 更新 UI
      });
    ```

## Metaprogramming / 元程式設計

- **簡介**:
  元程式設計是一種編寫能夠“操作其他程式”的程式的技術。這裡的“操作”可以是在編譯期或執行期間讀取、分析、生成或轉換程式碼。簡而言之，就是“關於程式的程式” (Program about programs) 或“寫程式來寫程式”。

- **演進歷史**:
  Lisp 語言是元程式設計的先驅，其“程式碼即數據”（Homoiconicity）的特性使得操作程式碼就像操作普通數據一樣自然。後來，不同的語言提供了不同形式的元程式設計能力，例如 C++ 的模板、Ruby 的動態方法、Python 的裝飾器和元類、以及 Java 的反射和註解處理。

- **核心概念**:
  - **反射 (Reflection)**: 程式在“執行期間”檢查自身結構和行為的能力。例如，獲取一個對象的所有方法名、動態調用方法、讀取註解等。
  - **程式碼生成 (Code Generation)**:
    - **編譯期**: 在程式編譯時生成額外的程式碼。例如 Java 的註解處理器 (Annotation Processor) 可以根據註解自動生成樣板程式碼。
    - **執行期**: 在程式運行時動態創建新的類、方法或函數。
  - **自省 (Introspection)**: 檢查程式碼對象（如類、函數、對象）的類型和屬性。反射是實現自省的一種機制。
  - **裝飾器/註解 (Decorators/Annotations)**: 一種將元數據附加到程式碼上的語法，通常用於觸發元程式設計的行為。

- **準則規範**:
  利用語言提供的機制，在編譯期或執行期對程式碼本身進行操作，以達到增加靈活性、減少重複程式碼（DRY）、創建領域特定語言（DSL）等目的。

- **優點**:
    - **DRY (Don't Repeat Yourself)**: 可以自動化生成大量樣板程式碼，減少手動編寫和維護的工作量。
    - **靈活性和擴展性**: 可以在不修改原始程式碼的情況下，為現有程式碼添加新功能（例如日誌、權限校驗、事務管理）。
    - **創建 DSL**: 可以創建更具表達力、更貼近業務領域的 API。

- **缺點**:
    - **複雜性**: 大大增加了程式碼的複雜度和理解難度，程式碼的行為可能不是表面看到的那樣。
    - **除錯困難**: 因為實際執行的程式碼可能是在編譯期或執行期動態生成的，所以除錯變得更加困難，錯誤信息可能晦澀難懂。
    - **性能影響**: 過度的反射或執行期程式碼生成會帶來顯著的性能開銷。
    - **工具支持**: IDE 的靜態分析、程式碼補全等功能可能對元程式設計支持不佳。

- **應用實例**:
  - **Python 裝飾器**: 用於為函數或類動態添加功能。

    ```python
    def log_execution_time(func):
        def wrapper(*args, **kwargs):
            import time
            start = time.time()
            result = func(*args, **kwargs)
            print(f"{func.__name__} executed in {time.time() - start}s")
            return result
        return wrapper

    @log_execution_time
    def expensive_operation():
        # ... some time-consuming code ...
        pass
    ```

  - **ORM 框架 (如 SQLAlchemy, Hibernate)**: 通過反射讀取類的定義，自動將對象映射到數據庫表。
  - **Web 框架 (如 Ruby on Rails, Django)**: 大量使用元程式設計來實現路由、模型驗證等功能，以減少樣板程式碼。
  - **C++ 模板元程式設計 (TMP)**: 在編譯期進行計算，可以用於優化、類型檢查等。

## Object-Oriented Programming, OOP / 物件導向編程

- **簡介**:
  物件導向編程是一種將真實世界的事物抽象為程式中的“對象”（Objects）的編程範式。程式被組織為一系列相互協作的對象的集合，每個對象都是數據（屬性）和操作這些數據的方法（行為）的封裝體。

- **演進歷史**:
  其思想最早起源於 1960 年代的 Simula 語言，用於進行物理世界的模擬。1970 年代的 Smalltalk 語言完善並發揚光大了 OOP 的核心概念，被認為是第一門純粹的物件導向語言。1990 年代，隨著 C++ 和 Java 的巨大成功，OOP 成為了軟體開發領域最主流的編程範式。

- **四大核心概念 (通常稱為四大支柱)**:
  1.  **封裝 (Encapsulation)**:
      - **定義**: 將數據（屬性）和操作數據的方法（行為）捆綁在一個稱為“對象”的單元中。
      - **目的**: 隱藏對象的內部實現細節，只對外暴露有限的接口（public 方法）。這可以保護數據不被外部隨意修改，降低了模塊間的耦合度。

  2.  **繼承 (Inheritance)**:
      - **定義**: 允許一個類（子類/派生類）獲取另一個類（父類/基類）的屬性和方法。
      - **目的**: 實現程式碼重用（DRY），並建立類之間的層次關係（“is-a” 關係）。例如，`Dog` is-a `Animal`。

  3.  **多型 (Polymorphism)**:
      - **定義**: "一個接口，多種實現"。它允許不同類的對象對相同的消息（方法調用）做出不同的、適合自身特性的響應。
      - **目的**: 增加程式的靈活性和可擴展性。調用者無需關心對象的具體類型，只需調用約定的接口即可。
      - **實現方式**: 通常通過方法重寫（Overriding）和接口實現（Interface Implementation）來實現。

  4.  **抽象 (Abstraction)**:
      - **定義**: 專注於對象的必要特徵（接口），而忽略其不相關的細節（實現）。
      - **目的**: 簡化複雜性。通過定義抽象類（Abstract Class）或接口（Interface），我們可以為一組相關的對象定義一個共同的藍圖，而無需關心每個對象的具體實現。

- **優點**:
    - **模組化和可維護性**: 非常適合構建大型、複雜的系統。類和對象提供了清晰的模塊邊界。
    - **高重用性**: 繼承和組合機制促進了程式碼的重用。
    - **可擴展性**: 通過多型和接口，可以很容易地添加新的功能模塊而不影響現有程式碼。
    - **貼近人類思維**: 將現實世界的問題映射到對象，使模型更易於理解。

- **缺點**:
    - **過度設計**: 對於簡單問題，OOP 可能顯得過於笨重和複雜。
    - **繼承問題**: 過深或不當的繼承層次會導致“脆弱的基類問題”（Fragile Base Class Problem），即父類的修改可能意外地破壞子類。
    - **狀態管理**: 對象自身管理狀態，在並發環境下，需要額外的同步機制（如鎖）來保證共享狀態的線程安全，這很複雜且容易出錯。
    - **樣板程式碼**: 有時需要編寫較多的樣板程式碼（如 getter/setter）。

- **應用實例**:
  - **主流語言**: Java, C++, C#, Python, Ruby, Swift 等都是強大的物件導向語言。
  - **應用領域**: 幾乎無處不在，包括企業級應用、GUI 框架、Web 框架、遊戲引擎、作業系統等。
  - **Java 範例**:

    ```java
    // 抽象：定義共同接口
    interface Animal {
        void makeSound();
    }

    // 封裝：數據和方法捆綁在類中
    class Dog implements Animal {
        private String name;

        public Dog(String name) { this.name = name; }

        // 多型：重寫接口方法
        @Override
        public void makeSound() {
            System.out.println("Woof!");
        }
    }

    class Cat implements Animal {
        private String name;

        public Cat(String name) { this.name = name; }

        @Override
        public void makeSound() {
            System.out.println("Meow!");
        }
    }

    // Main: 使用多型
    public class Main {
        public static void main(String[] args) {
            Animal myDog = new Dog("Buddy"); // Dog is-a Animal (繼承/實現)
            Animal myCat = new Cat("Mimi");

            myDog.makeSound(); // 輸出 "Woof!"
            myCat.makeSound(); // 輸出 "Meow!"
        }
    }
    ```

## Aspect-Oriented Programming, AOP / 斷面導向 / 面向切面編程

- **簡介**:
  AOP 是一種通過分離“橫切關注點”（Cross-cutting Concerns）來提高模組化程度的編程範式。它被認為是物件導向編程（OOP）的補充。在軟體開發中，有些功能（如日誌、安全、事務管理、性能監控）會散佈在系統的各個模塊中，AOP 的目標就是將這些散亂的功能抽取出來，使其成為獨立的、可重用的模塊。

- **演進歷史**:
  在 OOP 中，雖然類（Class）是很好的模塊化單元，但對於橫切關注點卻無能為力。例如，日誌功能可能需要在每個業務方法開始和結束時都插入程式碼，這導致了程式碼重複和核心業務邏D輯的混亂。AOP 的概念在 2000 年代初被提出，由 Gregor Kiczales 領導的團隊在 Xerox PARC 開發了 AspectJ，這是 AOP 最初和最著名的實現。

- **核心概念**:
  - **關注點 (Concern)**: 程式中我們感興趣的一部分功能。核心業務邏輯是一個關注點，日誌也是一個關注點。
  - **橫切關注點 (Cross-cutting Concern)**: 那些橫跨多個模塊、無法被乾淨地封裝在單個類中的功能。例如：日誌、權限驗證、事務管理、快取。
  - **切面 (Aspect)**: 對橫切關注點的模組化實現。一個切面封裝了“在哪裡”和“做什麼”的信息。
  - **連接點 (Join Point)**: 程式執行過程中的一個特定點，例如方法的調用、異常的拋出或字段的訪問。這是可以“織入”切面邏輯的地方。
  - **通知 (Advice)**: 切面的具體邏輯，以及它應該在何時執行。常見的通知類型有：
    - `Before`: 在連接點執行前執行。
    - `After`: 在連接點執行後執行（無論成功或失敗）。
    - `AfterReturning`: 在連接點成功執行後執行。
    - `AfterThrowing`: 在連接點拋出異常後執行。
    - `Around`: 環繞連接點執行，可以完全控制目標方法的執行。
  - **切點 (Pointcut)**: 一個表達式，用於精確地定義在“哪些”連接點（Join Points）上應用通知。它像一個查詢，用於篩選出目標方法。
  - **織入 (Weaving)**: 將切面（Aspect）應用到目標對象上，創建出最終代理對象的過程。織入可以在編譯期、類載入期或執行期進行。

- **優點**:
    - **增強模組化**: 使得核心業務邏輯更加純粹，因為輔助性功能被分離出去了。
    - **提高重用性**: 橫切關注點被封裝在切面中，可以在系統的不同部分重複使用。
    - **降低耦合度**: 業務模塊不再需要知道日誌、安全等細節，實現了更好的職責分離。
    - **易於配置和維護**: 可以集中管理橫切邏輯，方便統一修改和配置。

- **缺點**:
    - **增加複雜性**: 引入了新的概念，使得程式的執行流程變得不那麼直觀，增加了理解難度。
    - **除錯困難**: 如果出現問題，很難追蹤是原始程式碼的問題還是切面邏輯的問題。
    - **對工具的依賴**: 通常需要特定的框架（如 Spring）或工具（如 AspectJ 編譯器）來支持。

- **應用實例**:
  - **Spring Framework (Java)**: AOP 是其兩大核心之一（另一個是 IoC）。Spring AOP 被廣泛用於聲明式事務管理 (`@Transactional`)、安全控制 (`@PreAuthorize`)、日誌記錄等。
  - **AspectJ**: Java 語言的一個 AOP 擴展，提供了比 Spring AOP 更強大的功能（支持字段訪問等）。
  - **Python 的裝飾器** 和 **Ruby 的 mixin** 在概念上可以看作是 AOP 的一種輕量級實現。
  - **Spring AOP 偽代碼 (日誌切面)**:

    ```java
    @Aspect // 宣告這是一個切面
    @Component
    public class LoggingAspect {

        // 定義一個切點，匹配 service 包下所有類的 public 方法
        @Pointcut("execution(public * com.example.service.*.*(..))")
        private void serviceLayer() {}

        // 定義一個 "Before" 通知，在切點匹配的方法執行前執行
        @Before("serviceLayer()")
        public void logBefore(JoinPoint joinPoint) {
            String methodName = joinPoint.getSignature().getName();
            System.out.println("Executing method: " + methodName);
        }

        // 定義一個 "AfterReturning" 通知
        @AfterReturning(pointcut = "serviceLayer()", returning = "result")
        public void logAfterReturning(JoinPoint joinPoint, Object result) {
            String methodName = joinPoint.getSignature().getName();
            System.out.println("Method " + methodName + " executed successfully with result: " + result);
        }
    }
    ```

## Concurrent Programming / 並發編程

- **簡介**:
  並發編程是一種允許程式的不同部分在（看似）同一時間或在交錯的時間內向前推進的編程範式。它關注的是如何“結構化”程式，使其能夠同時處理多個任務。

  **區別並行 (Parallelism)**:
  - **並發 (Concurrency)**: 是關於“處理”多件事情。一個程式可以被設計成並發的，即使它運行在單核 CPU 上（通過時間分片快速切換任務）。
  - **並行 (Parallelism)**: 是關於“同時做”多件事情。它需要多核 CPU 或多台機器來真正地在同一時刻執行多個計算。
  - **關係**: 並行是實現並發的一種方式。一個好的並發設計可以更容易地利用並行來提高性能。

- **演進歷史**:
  早期作業系統就需要處理多個任務，並發的概念由此而生。隨著多核 CPU 在 2000 年代中期開始普及，為了充分利用硬體資源，並發編程從一個專業領域變成了主流開發者必須面對的課題。傳統的基於“線程和鎖”的模型被證明非常容易出錯，因此催生了許多更高級、更安全的並發模型，如 Actor 模型、軟體事務記憶體 (STM) 和通信順序進程 (CSP)。

- **核心概念與挑戰**:
  - **任務單元**:
    - **進程 (Process)**: 擁有獨立記憶體空間的執行單元，由作業系統管理，通信成本高。
    - **線程 (Thread)**: 在同一進程內共享記憶體空間的更輕量級的執行單元，通信成本低，但帶來了共享狀態的複雜性。
  - **共享狀態 (Shared State)**: 多個線程可以訪問和修改的數據。這是並發問題的萬惡之源。
  - **競爭條件 (Race Condition)**: 當多個線程同時訪問和修改共享數據，且最終結果取決於它們執行的精確時序時，就會發生競爭條件。
  - **死鎖 (Deadlock)**: 兩個或多個線程互相等待對方釋放資源，導致所有線程都被永久阻塞。
  - **同步機制 (Synchronization)**: 用於協調對共享狀態的訪問，以避免上述問題。常見的機制有：
    - **鎖 (Locks / Mutexes)**: 確保同一時間只有一個線程能訪問臨界區。
    - **信號量 (Semaphores)**: 允許多個線程訪問資源，但限制了最大數量。
    - **監視器 (Monitors)**: 將鎖和條件變量組合起來的更高級的同步原語。
    - **原子操作 (Atomic Operations)**: 不可中斷的操作，如 `compare-and-swap`。

- **優點**:
    - **提高響應能力**: 對於 GUI 應用或伺服器，可以將耗時操作放在後台線程，保持主線程響應。
    - **提高吞吐量**: 充分利用 CPU 等待 I/O 的空閒時間，或者利用多核 CPU 進行並行計算。
    - **任務模塊化**: 某些問題天然適合被分解為多個並發執行的任務。

- **缺點**:
    - **極度複雜**: 正確地編寫並發程式非常困難。競爭條件、死鎖等問題隱蔽性強，難以發現、重現和除錯。
    - **性能開銷**: 線程創建和上下文切換會帶來性能開銷。過度使用鎖會導致線程爭用，降低並行度。
    - **降低可組合性**: 兩個各自正確的並發模塊組合在一起，不一定能正確工作。

- **應用實例與模型**:
  - **共享內存與鎖模型 (Shared Memory & Locks)**:
    - **Java**: `Thread`, `synchronized`, `ReentrantLock`。
    - **C++**: `std::thread`, `std::mutex`。
    - **這是最傳統但也最難用的模型。**
  - **Actor 模型**:
    - **代表**: Erlang/Elixir, Akka (Scala/Java)。
    - **思想**: 程式由大量輕量級的 Actor 組成。每個 Actor 都有一個郵箱，它們之間通過發送異步消息來通信，不共享任何狀態。
  - **通信順序進程 (CSP)**:
    - **代表**: Go 語言的 Goroutines 和 Channels。
    - **思想**: "不要通過共享內存來通信，而要通過通信來共享內存。" (Don't communicate by sharing memory; share memory by communicating.) 任務之間通過顯式的通道 (Channel) 來傳遞數據。
  - **函數式方法**:
    - 由於函數式編程強調不可變性，從根本上避免了共享狀態的修改，因此非常適合並發編程。

## Generic Programming / 泛型編程

- **簡介**:
  泛型編程是一種編寫“類型無關”的算法和數據結構的編程範式。其目標是編寫一次程式碼，就可以安全地應用於多種不同的數據類型，而無需為每種數據類型都重寫一遍。它強調的是算法和數據結構的通用性，將其與所操作的具體數據類型解耦。

- **演進歷史**:
  泛型思想最早可以追溯到 1970 年代的 Ada 和 CLU 等語言。然而，真正使其發揚光大並影響深遠的是 C++ 的模板（Templates）機制，它在 1980 年代末被引入 C++。C++ STL (Standard Template Library) 的成功極大地展示了泛型編程的威力。後來，Java 在 1.5 版本中引入了泛型（Generics），C# 從 2.0 版本開始也內置了強大的泛型支持。

- **核心概念**:
  - **類型參數 (Type Parameters)**: 在定義函數、類或接口時，使用一個或多個佔位符（如 `<T>`）來代表一個未知的數據類型。這個佔位符在實際使用時會被一個具體的類型（如 `String`, `Integer`）替換。
  - **參數化多型 (Parametric Polymorphism)**: 這是泛型編程的理論基礎。它指的是函數或數據結構的行為對於所有（滿足某些約束的）類型都是統一的，不依賴於具體類型。
  - **泛型數據結構**: 可以存儲任意類型的數據結構，如 `List<T>`, `Map<K, V>`。
  - **泛型算法/函數**: 可以操作任意類型的數據的算法，如排序 `sort(List<T>)`。
  - **約束 (Constraints)**: 有時，泛型算法需要對類型參數有一些基本要求，例如，排序算法需要知道如何比較兩個元素。這時就需要對類型參數施加約束，要求它必須實現某個接口（如 Java 的 `Comparable<T>`）或滿足某些特性。

- **準則規範**:
  識別出算法或數據結構的核心邏輯，將其與所操作的數據的具體類型分離，通過類型參數來實現這種分離，並在必要時通過約束來保證算法的正確性。

- **優點**:
    - **程式碼重用 (DRY)**: 核心優勢。避免了為不同數據類型編寫大量重複的、僅類型不同的程式碼。
    - **類型安全**: 在編譯期就能捕獲類型不匹配的錯誤，而不是在執行期才拋出 `ClassCastException` 之類的錯誤。相比於使用 `Object` 或 `void*` 等頂級類型，泛型要安全得多。
    - **性能**: 在很多情況下（如 C++ 模板和 C# 泛型），泛型程式碼可以在編譯期被特化（Monomorphization），生成針對具體類型的高效程式碼，沒有執行期開銷。

- **缺點**:
    - **複雜性**: 過度使用或複雜的泛型（特別是帶有遞歸和複雜約束的）會使程式碼難以閱讀和理解。
    - **編譯時間和程式碼膨脹 (Code Bloat)**: 在 C++ 中，模板的實例化會為每個使用的具體類型都生成一份程式碼，可能導致編譯時間變長和最終的可執行文件變大。
    - **錯誤信息不友好**: 有時，泛型程式碼的編譯錯誤信息可能非常冗長和晦澀，難以定位問題根源。
    - **運行時限制 (Type Erasure)**: 在 Java 中，泛型信息在編譯後會被“擦除”，導致在運行時無法獲取到泛型的具體類型信息，這帶來了一些限制。

- **應用實例**:
  - **C++ STL (Standard Template Library)**: 泛型編程的典範，包含了大量的泛型容器（如 `std::vector<T>`, `std::map<K, V>`）和泛型算法（如 `std::sort`, `std::find`）。
  - **Java 集合框架**: `ArrayList<E>`, `HashMap<K, V>` 等都是泛型類。
  - **C# LINQ (Language-Integrated Query)**: 大量使用泛型和擴展方法來提供對各種數據源的統一查詢能力。
  - **Java 泛型方法範例**:

    ```java
    // 一個泛型方法，可以交換任意類型陣列中的兩個元素
    public class Utils {
        public static <T> void swap(T[] array, int i, int j) {
            T temp = array[i];
            array[i] = array[j];
            array[j] = temp;
        }
    }

    // 使用泛型方法
    String[] names = {"Alice", "Bob"};
    Utils.swap(names, 0, 1); // 正確

    Integer[] numbers = {1, 2};
    Utils.swap(numbers, 0, 1); // 正確

    // Utils.swap(names, 0, "wrong"); // 編譯錯誤，類型安全
    ```

## Evolutionary Map / 演進圖譜

1. 無結構時代：`命令式`（GOTO 跳來跳去）。
2. 結構化時代：`程序導向`（用函數封裝步驟）。
3. 封裝時代：`物件導向`（把數據和步驟包在一起）。
4. 去狀態時代：`函數式`（乾脆不要狀態，只求計算結果）。
5. 流與自動化時代：`反應式` / `宣告式`（關注數據流向與最終狀態）。

## Summary

1. 基礎邏輯類（計算的本質）

這類範式定義了程式碼如何與電腦硬體或邏輯規則互動。

| 範式名稱             | 核心思考模式                                       | 優點                           | 缺點                         | 舉例           |
| -------------------- | -------------------------------------------------- | ------------------------------ | ---------------------------- | -------------- |
| 命令式 (Imperative)  | 怎麼做 (How)：給予明確指令，手動更改記憶體狀態。   | 效能極高，對硬體控制精準。     | 程式碼冗長，容易產生副作用。 | C, Assembly    |
| 宣告式 (Declarative) | 做什麼 (What)：描述期望結果，隱藏具體過程。        | 代碼簡潔，易於閱讀。           | 底層黑盒，效能優化困難。     | SQL, HTML, CSS |
| 邏輯式 (Logic)       | 推理 (Inference)：定義事實與規則，由引擎推導結論。 | 適合處理複雜的約束與邏輯判斷。 | 搜尋空間大時效能極差。       | Prolog         |

2. 結構與組織類（代碼的佈局）

這類範式定義了如何封裝邏輯，是目前工程開發的主流。

| 範式名稱              | 核心思考模式                                     | 優點                             | 缺點                         | 舉例               |
| --------------------- | ------------------------------------------------ | -------------------------------- | ---------------------------- | ------------------ |
| 程序導向 (Procedural) | 分解步驟：將大任務拆解成一個個函數 (Procedure)。 | 結構清晰，適合中小型邏輯。       | 數據與函數分離，維護困難。   | C, Fortran         |
| 物件導向 (OOP)        | 封裝物件：將數據 (屬性) 與行為 (方法) 綁在一起。 | 重用性高，適合大型團隊協作。     | 層次設計過深會導致過度設計。 | Java, Python, C#   |
| 泛型編程 (Generic)    | 類型抽象：編寫不依賴具體型別的通用演算法。       | 極大減少代碼重複，維持類型安全。 | 編譯報錯非常難以解讀。       | C++ Template, Rust |

3. 數據與流向類（狀態的管理）

這類範式關注數據如何隨時間或事件流動，是處理高併發與即時系統的關鍵。

| 範式名稱                | 核心思考模式                                      | 優點                         | 缺點                         | 舉例                    |
| ----------------------- | ------------------------------------------------- | ---------------------------- | ---------------------------- | ----------------------- |
| 函數式 (Functional)     | 數學映射：數據不可變，無副作用，只有輸入輸出。    | 極易進行並行運算與單元測試。 | 遞迴與抽象代碼學習曲線高。   | Haskell, Scala, Lisp    |
| 事件導向 (Event-Driven) | 非同步觸發：主程式等待事件，觸發後執行回調。      | 響應性高，不會阻塞執行緒。   | 邏輯分散，容易陷入回調地獄。 | Node.js, GUI 程式       |
| 反應式 (Reactive)       | 數據流傳播：像 Excel 公式一樣，數據變動自動傳播。 | 適合處理即時數據流。         | 數據流向難以追蹤、調試困難。 | RxJS, Vue.js            |
| 並發式 (Concurrent)     | 多工並行：處理多個執行單元間的同步與通訊。        | 提升多核 CPU 效率。          | 易產生死鎖 (Deadlock)。      | Go (Goroutines), Erlang |

4. 高階與輔助類（程式的自我演進）

這類範式通常作為補充，用於優化程式碼架構。

| 範式名稱                 | 核心思考模式                                 | 優點                         | 缺點                           | 舉例                         |
| ------------------------ | -------------------------------------------- | ---------------------------- | ------------------------------ | ---------------------------- |
| 元編程 (Metaprogramming) | 程式寫程式：程式在執行或編譯時修改自身行為。 | 極致抽象，適合開發框架。     | 程式碼「不見即所得」，難閱讀。 | Python Decorator, Ruby       |
| 斷面導向 (AOP)           | 橫切關注點：將日誌、安全檢查等從主邏輯剝離。 | 保持核心代碼乾淨，方便維護。 | 增加系統透明度下降，調試難。   | Spring (Java), Python 裝飾器 |
